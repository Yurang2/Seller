# 구현 중 설계 확인

작성: 2026-09-16 · 기준 브랜치 `claude/hopeful-wright-olq2lc`

2026-09-16 사용자 지시 “사이트 마저 구현. 클라우드플레어는 이따 해도 됨”에 따라 아래 안건을 채택한다. R-01~R-14를 완화하지 않는다. 원격 배포 검증은 운영 배포 전 필수로 남긴다.

## IMP-01 · M0 조사 가져오기에 필요한 테이블 생성 시점 — 채택

- **제안:** 골격 완료 후 M0에서 상품·캐릭터·요건·공급처·오퍼·배송 시나리오의 저장 테이블을 생성한다. 데이터 모델은 유지하고, 상품 조사 전용 화면과 원가 기능은 M1에서 구현한다. 주문·자동화 화면은 만들지 않는다.
- **근거:** PLAN 12장의 M0 수용 기준은 템플릿 행을 해당 엔티티로 가져오도록 요구하나, ARCHITECTURE 7장은 해당 테이블을 M1 이후로 분류한다. 임시 JSON에 넣으면 참조 무결성과 같은 도메인 함수 사용 규칙을 충족하기 어렵다.
- **대안:** M0에서는 가져오기 미리보기만 만들고 적용을 M1로 미룬다. 이 경우 M0 수용 기준의 순서를 변경해야 한다.

## IMP-02 · 최신 결정과 미확인 선택값 보존 — 채택

- **제안:** 초기 결정 D-03·D-04·D-05는 PLAN 2.4 및 ARCHITECTURE의 채택 상태로 입력하고, SEED 8장의 이전 제안 내용은 맥락으로 보존한다. 사업 모델 선택값에 PLAN의 `domestic_wholesale`(국내 정식 도매), 오퍼 배송 포함 범위·옵션에 `unknown`을 추가한다. 초기 사업 모델은 `undecided`로 유지한다.
- **근거:** SEED 8장은 이전 제안 상태이지만 PLAN 13장은 사용자 채택을 명시한다. DATA_MODEL의 사업 모델 enum에는 국내 정식 도매가 없고, 오퍼의 배송 범위·옵션 enum에는 SEED/조사 시트에 실제 존재하는 미확인을 표현할 값이 없다. 미확인을 `none` 또는 `single`로 바꾸면 기록 원칙을 위반한다.
- **대안:** 모든 이전 결정을 제안 상태로 입력하고 국내 정식 도매 선택 및 미확인 오퍼의 가져오기를 차단한다. 최신 결정이 반영되지 않고 M0 가져오기에서 유효한 초기 행이 실패한다.

## 진행 원칙

- 골격 12장 2번의 원격 DB 적용 및 5번의 배포·Access 검증은 실제 확인 결과만 완료로 기록한다.
- 로컬 성공이나 테스트 통과를 원격 검증의 대체로 표시하지 않는다.
- 사용자 확인이 필요한 변경은 승인 전 코드에 적용하지 않는다.

## IMP-03 · 원격 Access 검증 시점 — 채택 (원격 검증 보류)

- **제안:** 현재 골격 기준 1·2·3·4·6은 실제 검증했다. 5번(배포 후 모든 경로 Access 로그인 강제)은 최초 운영 배포 직전의 필수 차단 기준으로 유지하되, 사용자 확인이 있으면 M0·M1 로컬 구현을 먼저 진행한다. 운영 배포는 5번이 끝나기 전 허용하지 않는다.
- **근거:** 전용 원격 D1 생성·마이그레이션은 성공했다. 그러나 현재 Cloudflare 토큰의 R2 버킷 생성 요청은 Authentication error(10000), Access 조직 조회는 403이며, Access 앱은 없다. 앱 코드만으로 외부 계정의 권한·설정과 실제 로그인을 검증할 수 없다. 로컬 API의 미인증·위조 JWT 거절은 테스트됐으나 원격 보호 검증과 동일하지 않다.
- **대안:** 문서의 순서를 그대로 유지한다. Cloudflare 권한과 Zero Trust 팀 도메인·허용 이메일을 준비하고, R2/Worker/Access 배포 검증을 완료한 뒤 M0에 착수한다.
- **현재 처리:** 사용자 지시에 따라 IMP-01·02의 문서 차이 처리 및 IMP-03의 로컬 M0·M1 선행을 적용한다. 원격 배포는 보류한다.

## IMP-04 · 게이트 집계는 "어떤 항목이든 fail이면 fail" — 채택 (2026-09-18, 검토 반영)

- **제안:** PLAN 2.2의 "세 항목 fail만 전체 fail"보다 엄격하게, 13개 항목 중 하나라도 fail이면 프로필 fail. 수동 판정(`gate_set_by=manual`)은 두지 않는다.
- **근거:** 채널 정책 위반이나 반품 불능도 판매를 막는 사유다. 항목별 판정에 이유가 남으므로 수동 집계가 필요 없다.
- **대안:** 문서대로 세 항목만. 나머지 fail을 조건부로 낮추면 실패 사유가 흐려진다.

## IMP-05 · 근거의 질 검사 — 채택 (2026-09-18, 검토 반영)

- **제안:** ① 첨부는 같은 기록에 올린 파일만 인정하고 가격·견적·세율·수수료 증빙은 이미지·PDF만 허용. ② 위험도 높음 요건 항목의 통과·조건부는 확인 상태 답변 + 첨부 또는 evidence_for 링크 필요, 직접 세운 가정으로는 낮음이 아닌 항목을 통과시킬 수 없음. ③ 조사→원가확인 전이는 실결제가 근거 자체에 캡처가 붙은 오퍼 필요. ④ 내 정책값(가정 판매가·청구 배송비·광고비·고정비)은 첨부 대상에서 제외.
- **근거:** 검토 보고 P1. 규칙의 형식만 지키고 실질을 우회하는 경로를 막는다. ④는 내가 정하는 값에 외부 증빙을 요구하는 과잉을 없앤다.
- **대안:** 경쟁사 관찰만 거부(기존). 가정 답변으로 13개 항목을 전부 통과시킬 수 있어 게이트가 무의미해진다.

## IMP-06 · 단계 전이 검사 범위 — 채택 (2026-09-18)

- **제안:** 앞으로 갈 때 "새로 들어가는 단계"의 조건만 검사한다. 일시정지·보류에서 복귀할 때는 전 구간을 검사한다.
- **근거:** PLAN 7.1의 표는 단계별 진입 조건이다. 매 전이마다 전 단계를 재검사하면 등록 준비→판매 중에서 견적 첨부를 다시 요구하는 중복이 생긴다. 오래된 견적은 신선도 경고와 재확인 작업이 맡는다.
- **대안:** 누적 재검사.

## IMP-07 · M2 등록 상품(listings) 범위 — 채택 (2026-09-18)

- **제안:** 채널 등록 상품 기록·판매 중 전이·수동 절차(SOP) 2종·홈 "판매 개시까지" 위젯. 주문·정산은 M3로 보류. 채널 API 연동 없음(`integration_state=none` 배너와 수동 절차 링크).
- **근거:** 사용자 목표 "지금 당장 플랫폼에 올리기"에 필요한 최소 구성. 실제 등록은 채널 판매자 센터에서 사람이 하고, 앱은 그 결과를 규칙(결정 판매가 일치, 이미지 출처, 노출 확인일)과 함께 기록한다.

## IMP-08 · 실행 방식과 "에어테이블식 적재" — 제안 (2026-09-18, 사용자 확인 대기)

- **제안:** 터미널 서버 대신 데스크톱 앱(Electron)으로 포장하되 저장소 바인딩만 어댑터로 바꿔 Workers 빌드와 호환을 유지한다. 에어테이블은 저장소로 쓰지 않고, 표 화면과 사용자 정의 열을 앱 안에 만든다. 상세는 `PLAN_NEXT.md`.
- **근거:** 사용자가 서버 실행을 거부했다. 에어테이블은 미확인≠0, 첨부 검증, 전이 조건 같은 규칙을 강제할 수 없고 데이터를 둘로 가른다. 표 화면은 데이터베이스 위의 표현 층이므로 지금 앱과 같은 층에서 해결된다.
- **대안:** Cloudflare 배포 우선(원래 D-05). 터미널이 없어지고 폰에서도 열리지만 계정 설정과 로그인 보호 검증이 선행돼야 한다. 사용자가 원하면 트랙 C로 켠다.

## IMP-09 · 포트 없는 데스크톱 개발 모드 — 철회 (2026-09-19, 트랙 A 보류로 불필요)

- **제안:** A-3의 `desktop:dev`는 Vite 빌드 감시와 Electron 창 자동 새로고침으로 구현한다. 개발 중에도 포트를 열지 않으며, React 상태를 유지하는 HMR 대신 수정 시 화면을 다시 읽는다. 배포 앱은 A-2 그대로 `protocol.handle`에서 `app.fetch`를 호출한다.
- **근거:** A-2 및 사용자 지시는 Electron이 포트를 열지 않도록 요구하지만, A-3의 통상적인 Vite HMR은 HTTP/WebSocket 서버를 사용한다. 빌드 감시는 두 실행 모드 모두 같은 프로토콜 경로를 검증하고 별도 서버 없이 수정 결과를 반영한다.
- **대안:** Vite HMR 통신을 Electron IPC로 운반하는 별도 전송 계층을 구현한다. 포트 없이 상태 보존 HMR이 가능하지만 개발 전용 통신 계층과 추가 검증이 필요하다. 또는 개발 모드에만 루프백 포트를 허용한다(명시적 사용자 승인 필요).
- **적용:** 사용자 답변 전까지 해당 개발 모드 변경을 적용하지 않는다. 저장소 어댑터와 배포 셸 구현은 원래 계획대로 진행한다.

## IMP-10 · 휴대폰 사용을 위한 웹 배포 우선 — 채택 (2026-09-19, Fable 검토: PLAN_NEXT v2)

- **제안:** 사용자님의 PC·휴대폰 사용 요구에 맞춰 트랙 A의 포장 작업을 중단하고 트랙 C(Cloudflare 웹 배포 및 Access 인증 검증)를 먼저 진행한다. PC·휴대폰이 같은 Workers API·D1·R2 저장소를 사용한다. A-4 미충족 항목을 완료로 표시하거나 B로 넘어가지 않는다. 현재 데스크톱 작업은 보존하고, 실제 채택·배포·기존 데이터 이전은 사용자 확인 후 진행한다.
- **근거:** 사용자님이 휴대폰에서도 Seller 활동을 하고 싶다고 밝혔다. 현재 A는 로컬 SQLite·첨부 폴더를 쓰는 단일 PC 앱이고, PLAN_NEXT는 데스크톱과 클라우드의 동기화를 설계하지 않는다. 같은 기록을 여러 기기에서 이어서 쓰려면 중앙 저장소와 인증된 웹 접근이 필요하다. 기존 Workers 빌드와 API 테스트는 현재 작업 중에도 통과했다.
- **대안:** A를 먼저 완성하고 기기 간에는 ZIP 백업·복원을 수동 사용한다(서로 다른 최신 기록이 생길 수 있음). 또는 데스크톱과 모바일을 위한 별도 동기화를 설계한다(충돌 처리·오프라인 변경·첨부 동기화 범위 추가). PC 상시 실행과 외부 접속으로 로컬 앱을 노출하는 방식은 기본안으로 삼지 않는다.
- **선행 조건:** Cloudflare 배포 권한·D1/R2·사용 도메인 및 Access 로그인 정책을 확인하고, 홈·정적 파일·미등록 경로·API 전체에 대한 비로그인 차단을 실제 검증한다. 모바일 화면과 첨부 업로드·다운로드·백업 사용성도 실제 확인한다. 기존 R-01~R-14는 유지한다.
- **현재 상태:** 순서 변경 미승인. 데스크톱 코드와 설치 파일은 작업 폴더에 보존했으며 아직 커밋·푸시하지 않았다. 실제 Windows 설치·바탕화면 실행 검증은 미완료다.

## IMP-11 · 데스크톱 어댑터 코드 보존 — 채택 (2026-09-19)

- **제안:** 트랙 A 코드(`src/platform`, `electron`, `tests/platform`)를 삭제하거나 분리하지 않고 보존한다. `pnpm test`에 데스크톱 테스트 23개를 포함한 채 둔다.
- **근거:** Workers 번들에 네이티브 의존성이 들어가지 않는 구조라 웹 빌드에 영향이 없다. 트랙 D(가격 감시 PC 보조 프로그램)에서 재사용한다. A-4 완료 기준 미충족은 그대로 기록한다.
- **대안:** 별도 브랜치로 격리. 두 브랜치 유지 비용이 생기고 재사용 시 병합 충돌이 난다.
