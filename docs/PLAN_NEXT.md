## 왜 순서가 바뀌는가

- PC와 폰이 같은 기록을 봐야 한다. 데스크톱 앱(트랙 A)은 PC 한 대의 SQLite 파일에 데이터를 두므로 폰에서 볼 수 없고, 두 기기 동기화를 설계하면 충돌·유실 문제와 두 번째 규칙 계층이 생긴다.
- 사용자님이 "서버를 돌리기 싫다"고 하신 것은 터미널 실행을 말한다. Cloudflare에 올리면 사용자님이 아무것도 실행하지 않는다. 주소 하나를 PC와 폰에서 연다.
- 따라서 원래 기획서의 D-05(Cloudflare)로 돌아간다. 새 순서: **C(인증된 웹 배포) → M(모바일 핵심 작업 실기기 검증) → B(표 화면·사용자 정의 열)**. A는 보류(코드 보존), D는 설계 메모 유지.

## 트랙 A 처리: 보류, 코드 보존

- `src/platform/*`, `electron/*`, `tests/platform/*`, `electron-builder.yml`, `vite.desktop.config.ts`는 그대로 둔다. Workers 번들에 네이티브 의존성이 들어가지 않는 구조(`platform/orm.ts`의 등록 방식)라 웹 빌드에 영향이 없고 테스트 88개가 통과한다.
- `pnpm desktop:build`·`desktop:backup:verify`는 문서에 "보류·미검증"으로 남긴다. A-4 미충족 항목은 완료 처리하지 않는다. `desktop:dev`(IMP-09)는 만들지 않는다.
- 데스크톱을 다시 켜는 조건: 사용자님이 "폰 없이 PC만" 또는 "오프라인 필수"로 요구를 바꿀 때. 그때도 클라우드 기록을 ZIP으로 옮기는 방식이며 동기화는 설계하지 않는다.

## 트랙 C · Cloudflare 배포와 로그인 보호 (먼저)

### C-0 사용자님이 준비할 것 (Astra가 대신 못 함)
1. Cloudflare 계정(무료). 대시보드에서 **Zero Trust** 활성화(Free 플랜, 50명까지 무료).
2. Astra가 배포할 수 있게 둘 중 하나: (a) 사용자님 PC에서 `wrangler login`으로 브라우저 로그인, 또는 (b) 대시보드에서 API 토큰 발급(권한: Workers Scripts 편집, D1 편집, R2 편집, Access: Apps and Policies 편집, Account Settings 읽기). 토큰은 대화나 Git에 넣지 않고 `.dev.vars`나 환경변수로만.
3. 로그인에 쓸 이메일 1개.

### C-1 배포 절차 (Astra)
1. 원격 D1 `seller-db`는 이미 있다(wrangler.jsonc의 database_id). 마이그레이션 0001~0003을 `pnpm db:migrate:remote`로 적용하고 결과를 기록한다.
2. R2 버킷 `seller-attachments`, `seller-backups` 생성.
3. `wrangler deploy`. 배포 주소는 `seller.<계정>.workers.dev`(사용자 도메인이 있으면 그것). 커스텀 도메인은 필수 아님.
4. Zero Trust → Access → Applications → Self-hosted: 배포 도메인 전체(`/`)를 보호. 정책: 사용자님 이메일만 허용, 인증은 이메일 일회용 코드(OTP). 세션 길이 30일(폰에서 자주 로그인하지 않도록).
5. Access 앱의 AUD 태그와 팀 도메인을 `wrangler.jsonc` vars(`ACCESS_AUD`, `ACCESS_TEAM_DOMAIN`)에 넣고 재배포. `APP_ENV`는 `production`이어야 한다(데스크톱·개발 우회 금지).
6. 원격에서 "초기 조사 기록 불러오기"를 실행한다. 로컬에 실제 입력한 기록이 있으면 로컬 ZIP 내보내기 → 원격 복원으로 옮기고, 없으면 시드만.

### C-2 서버 백업 (웹에서는 종료 훅이 없다)
- 첫 Job이자 유일한 Job: `backup_export`. Cron `0 18 * * *`(한국 03:00). 기존 `exportArchive`를 호출해 `BACKUPS` 버킷에 `backups/YYYY-MM-DD.zip` 저장, 30개 유지. 실행 결과는 `job_runs` 테이블에 남긴다(ARCHITECTURE 8장 구조를 이 Job 하나 분량만 먼저 만든다).
- 화면 "백업·복원"에 서버 백업 목록(날짜·크기·상태)과 다운로드·"이 백업으로 복원(미리보기 → 적용)" 버튼. 마지막 백업이 48시간 넘게 없으면 홈에 경고. 실패한 실행은 홈 자동화 위젯에 "실패 · 사유"로 표시한다(R-10: 실행 코드가 있으니 cron 선언을 되살린다).
- `readiness_items.backup_verified`는 원격 백업 ZIP을 빈 로컬 DB에 복원해 비교했을 때만 완료(기존 `backup:verify`를 원격 ZIP 입력으로도 돌릴 수 있게 옵션 추가).

### C-3 완료 기준
1. 로그인하지 않은 브라우저에서 `/`, `/assets/...`, `/아무경로`, `/api/v1/health` 모두 Access 로그인 화면으로 간다(폰·PC 각각 확인). Access를 우회해 Worker 주소로 직접 접근하는 경로가 없어야 한다(워커 라우트가 Access 뒤에만 있음을 확인).
2. 이메일 코드로 로그인하면 홈이 뜨고, 초기 조사 기록이 있다.
3. 폰에서 첨부(사진) 업로드와 다운로드가 된다.
4. 서버 백업이 한 번 실제로 생성됐고, 그 ZIP을 빈 로컬 DB에 복원해 같은 기록이 나온다. `backup_verified` 완료.
5. `pnpm test`·`pnpm build` 통과. IMPLEMENTATION_STATUS에 배포 주소(계정 식별자는 가려서), Access 설정, 검증 결과를 실제 확인한 것만 적는다.

## 트랙 M · 모바일 핵심 작업 (실기기 검증)

폰에서 하는 일은 "조사"가 아니라 **포착·확인·응답**이다. 아래 다섯 가지만 폰 폭(390px)에서 막힘 없이 되게 한다. 나머지 화면은 깨지지 않으면 된다.

| 순위 | 활동 | 화면 변경 |
|---|---|---|
| 1 | 할 일·막힘 확인, 완료 처리 | 홈 상단에 "오늘 할 일" 압축 카드. 작업 상세에서 상태 변경(이유 입력) 버튼을 엄지 위치(하단 고정)에 |
| 2 | 상품 링크·메모 빠른 기록 | 홈에 "빠른 기록" 버튼: 링크 붙여넣기 + 한 줄 메모 → `products`(발견 단계) 또는 `notes`(일지) 선택. 이유는 "빠른 기록"으로 자동 채움(R-06 유지: 자동 문구도 기록되는 이유다) |
| 3 | 증빙 사진 캡처 업로드 | ClaimEditor 파일 입력에 `accept="image/*,application/pdf" capture="environment"`. 업로드 후 즉시 상태를 확인으로 바꿀 수 있게 |
| 4 | 요건 답변 입력 | 요건 항목 상세를 폰에서 한 화면에: 답변 Claim 편집 + 판정 저장 |
| 5 | 등록 상품 상태 변경 | 등록 상품 상세의 상태 변경(판매 중·일시정지·종료)을 하단 고정 버튼으로 |

공통: 폰에서는 좌측 사이드바 대신 하단 탭(홈·상품·할 일·근거·더보기). PWA 매니페스트와 아이콘(홈 화면에 추가). **오프라인 기능·푸시 알림·네이티브 앱은 범위에 넣지 않는다.**

완료 기준: 사용자님 실제 폰에서 위 다섯 활동을 순서대로 한 번씩 수행한 기록(각 활동의 활동 로그 ID)을 IMPLEMENTATION_STATUS에 남긴다. 화면 캡처는 증빙으로 첨부한다.
